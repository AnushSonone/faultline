## Root-cause evaluation on REAL data (RCAEval RE2-OB, Phase A)

15 real fault-injection cases (5 services x cpu/mem/delay, instance 1) from RCAEval-v2
(Figshare file 60960049, sha256 72006b45..., MIT license), converted by
`python -m faultline_data.adapters.rcaeval` (traces sampled 1/8 by whole trace, logs capped;
sampling recorded per-incident in labels notes). Untuned spec-18.4 weights, labels hidden
from the pipeline:

| metric | value |
|---|---|
| top-1 accuracy | 0.267 |
| top-3 accuracy | 0.467 |
| MRR | 0.407 |

Per fault type (n=5 each): cpu top-1 0.20, delay top-1 0.20, mem top-1 0.40.

Ablations (top-1): no_change_proximity 0.27, no_critical_path 0.27, no_failed_trace_coverage 0.27, no_log_evidence 0.27, no_temporal_precedence 0.13, no_topology 0.07.

**Honest read:** the untuned deterministic pipeline is far weaker on real data than on the
synthetic suite - 26.7% top-1 vs 100%. Ablations show which features actually carry real-data
ranking: topology consistency (remove it: 26.7% -> 6.7%) and temporal precedence (-> 13.3%).
Change proximity, log evidence, failed-trace coverage, and critical-path contribution move
nothing here: RCAEval has no deployment events, and status codes plus sampled traces carry
little error signal for these fault types. For external context, the RCAEval paper (WWW'25,
arXiv 2412.17015) reports coarse-grained RE2 results on Train Ticket, not Online Boutique, as
Avg@5: CIRCA 0.46, RCD 0.54 - a different system and metric, so not directly comparable to the
top-1 numbers above. No published AC@1 for RE2-OB exists to compare against; any baseline
comparison must come from running the RCAEval harness locally under the same protocol.
Improving real-data accuracy (metric-name semantics, trace latency deltas as anomaly input,
tuned weights on a training split) is future work and must be reported against these same
untuned numbers.

## Engine benchmarks (TA-049)

**Withdrawn pending a harness fix - no throughput or speedup numbers are claimed.** The
previously published table (5.7x-15.3x batching speedups) was an instrumentation artifact:
`crates/cli/src/bench.rs` took two `Instant::now()` readings plus a `Vec::push` per chunk
inside the timed loop, so at batch size 1 the reported throughput absorbed ~40ns/row of timer
overhead. Baseline-minus-batched was a near-constant 32-40 ns/row across workloads - a fixed
per-iteration cost, not a batching win. Two of the workloads (`filter_heavy`,
`aggregation_heavy`) were also loops local to the bench harness that touched no engine
operator. The corrected harness must time each whole pass once and benchmark actual operators;
the table returns when those numbers exist. Raw (invalid) outputs remain in `benchmarks/` for
the record.
